# Defects - jupyterlab_export_svg_as_png_extension

`[ ]` open, `[x]` fixed. Dated notes under each track how it evolved.

## Context menu

- [x] `DEF-1` **Copy/Save as PNG shown on markdown content holding no SVG** - MEDIUM; in the Markdown Viewer the two items appear enabled when the right-click lands on the container (left gutter, gap between blocks, area below the last block) and export an unrelated diagram from elsewhere in the document; cause: `findSvgTarget()` scanned the clicked element's descendants (`target.querySelector('svg')`, `target.querySelectorAll('img')`), so a click on `div.jp-RenderedMarkdown` matched every image in the whole document; fix: search only the clicked element and its ancestors (direct `IMG` check plus `target.closest('svg')`); `src/index.ts`
  - 2026-08-21 reported: two different menus on the same document alternating with small pointer movements; confirmed deterministic over five Playwright-driven clicks with the `contextmenu` target captured in a capture-phase listener - `div.jp-RenderedMarkdown` gives the items, `p` does not
  - 2026-08-21 ruled out: listener ordering; the plugin's bubble-phase `contextmenu` handler is registered during activation and always runs before Lumino builds the menu, so `lastContextMenuTarget` is fresh
  - 2026-08-21 attempted: descendant scan removed from `findSvgTarget()`; awaiting verification against the live server
  - 2026-08-21 details: full root-cause and repro study in [DEF-1 details](defects/DEF-1-context-menu-targeting.md)
  - 2026-08-21 fixed (v1.1.7): descendant scan removed; verified in browser - gutter, block gap, paragraph, heading and below-last-block all hide the items, SVG image and mermaid diagram show them and export the clicked graphic
- [x] `DEF-2` **inert mermaid suppression guard** - LOW; `hasMermaidExtension()` tested `mermaid:copy-as-png` / `mermaid:download-as-png`, command ids no deployed extension registers (JupyterLab 4.6.3 core ships only `mermaid:copy-source`, and `jupyterlab_mmd_to_png_extension` is deprecated and not installed), so the whole markdown-suppression branch in `shouldShow()` was unreachable; fix: guard and `isInMarkdownContext()` removed, `shouldShow()` reduced to the target test which `DEF-1` made sufficient; `src/index.ts`
  - 2026-08-21 reported: found while root-causing `DEF-1`; a silently inert guard would not catch the duplicate-entry problem it was written for
  - 2026-08-21 attempted: branch deleted rather than re-pointed at live command ids, since the extension it guarded against is superseded by this one
  - 2026-08-21 fixed (v1.1.7): guard and isInMarkdownContext removed; no duplicate entries observed on a mermaid diagram alongside core's Mermaid Copy Diagram Source
- [x] `DEF-3` **over-corrected DEF-1 fix hid the items inside single-graphic containers** - MEDIUM; after DEF-1 the items were hidden for any click that missed the graphic itself, including the image viewer panel (image occupies 17.7% of it), a notebook SVG output box, a mermaid wrapper and the paragraph around a markdown image; cause: the descendant search was removed wholesale rather than scoped; fix: search descendants again but only inside containers built to hold one graphic (`SINGLE_GRAPHIC_HOLDERS`) and only when the container holds exactly one, with `.jp-RenderedMarkdown` deliberately excluded so DEF-1 stays fixed; `src/index.ts`
  - 2026-08-21 reported: found by adversarial review before release; measured live - right-clicking 30px beside a notebook plot, or anywhere in the image viewer panel, offered nothing
  - 2026-08-21 fixed (unreleased): scoped holder search added; regression covered by 'offers both items beside the diagram in its wrapper' and 'offers both items in the empty panel area'
  - 2026-08-21 fixed: verified: 12/12 galata green; mutation restoring the unbounded scan turns only the DEF-1 guard test red
- [x] `DEF-6` **a non-SVG image inside a single-graphic container exported its neighbour** - CRITICAL; right-clicking a raster `<img>` that sat in a holder alongside an SVG one offered both items and saved the SVG, so the user right-clicked a PNG and received a PNG of the image next to it with no indication; cause: an `<img>` failing `isImgSvg()` fell through to the holder branch instead of stopping; fix: a click that lands on an image resolves to that image or to nothing, never to the holder search; `src/index.ts`
  - 2026-08-21 reported: found by adversarial review before release; reproduced end-to-end on a plain `.md` in Markdown Preview - a `<figure>` holding chart.svg and raster.png, right-click the raster, `Save as PNG` yields 1920x1248, the chart's aspect
  - 2026-08-21 fixed (unreleased): early return added at the IMG branch
  - 2026-08-22 not pinnable under the current holder list: removing the early return leaves the suite green, because the `DEF-8` fix (dropping `figure`) already stops the fall-through. No container JupyterLab builds holds a raster and an SVG together, so the guard is defensive. The end-to-end record of the reported symptom is 'hides both items on the raster image beside an SVG', which needs both fixes undone before it fails
- [x] `DEF-7` **a decorative inline `<svg>` outranked the real graphic** - CRITICAL; inline SVG was counted before images, so the sole `<svg>` in a holder won even when the holder's actual graphic was an `<img>`; a caption icon, sparkline or legend glyph beside the figure was exported in its place; cause: two separate exactly-one tests instead of one over both kinds; fix: inline SVG and SVG images counted together, resolving only when the total is exactly one; `src/index.ts`
  - 2026-08-21 reported: found by adversarial review before release; reproduced in a trusted notebook `text/html` output - a 12x12 red dot in the figcaption beside a 400x260 chart exported as 1920x1920, the dot
  - 2026-08-21 fixed (unreleased): unified count added
- [x] `DEF-8` **`figure` treated as a single-graphic container** - MAJOR; `<figure>` is a generic HTML grouping element - the spec's own examples wrap tables, code listings and quotations - so a right-click on a table cell inside one offered both items and exported a 10x10 status icon from another cell; cause: `figure` was in `SINGLE_GRAPHIC_HOLDERS` on the assumption it always wraps one graphic; fix: `figure` removed; the mermaid case it was meant to serve is already covered by `.jp-RenderedMermaid`; `src/index.ts`
  - 2026-08-21 reported: found by adversarial review before release; reproduced with a status table inside a figure
  - 2026-08-21 fixed (unreleased): holder list reduced to the three containers JupyterLab itself builds around one graphic; regression covered by 'hides both items on the caption'
- [x] `DEF-9` **a nested `<svg>` made a one-graphic container count as two** - MAJOR; `querySelectorAll('svg')` counts the whole subtree, and nested `<svg>` viewports are legal and routine in hand-authored and tool-generated diagrams, so a single such diagram counted as two and near-miss clicks - the caption, the output-box padding - went hidden; that is the DEF-3 regression still open for any nested-viewport graphic; fix: count only the outermost `<svg>` elements; `src/index.ts`
  - 2026-08-21 reported: found by adversarial review before release; measured - one 300x200 diagram with a single nested `<svg>` counts as 2 in both a `<figure>` and a `.jp-RenderedSVG` box
  - 2026-08-21 fixed (unreleased): outermost-only filter added
- [x] `DEF-12` **comment above `findSvgTarget()` described the opposite of the code** - LOW; it stated descendants are deliberately not searched, sitting directly above the two `querySelectorAll` calls added by the DEF-3 fix, so a reader auditing the DEF-1 guarantee would stop there and never reach the branch where DEF-6 to DEF-9 all lived; fix: comment rewritten to describe the two-stage resolution actually implemented; `src/index.ts`
  - 2026-08-21 reported: found by adversarial review before release; same class as DEF-2, re-introduced on the same function by the fix for DEF-3
  - 2026-08-21 fixed (unreleased)
- [x] `DEF-13` **the DEF-11 coordinate fallback exported a graphic the user never right-clicked** - CRITICAL; the fallback accepted any element at the recorded point whose `.jp-MainAreaWidget` id matched, which proves same document, not same graphic; a re-render that also changed layout slid a different graphic under the point and exported it silently; fix: the resolved graphic is fingerprinted when it is resolved from the live node (`img` src, or the serialised markup for inline SVG) and the fallback returns null unless the re-derived graphic matches; `src/index.ts`
  - 2026-08-22 reported: found by adversarial review before release; reproduced in a trusted notebook - right-click a 400x260 chart, let the output above it re-render shorter, `Save as PNG` yields 1920x1920, the square from the next cell
  - 2026-08-22 fixed (unreleased): identity gate added on top of the widget-id gate; regression covered by 'refuses to export a different graphic that took the same place'
- [x] `DEF-14` **a click inside a nested `<svg>` viewport exported the sub-viewport** - MAJOR; `target.closest('svg')` returns the innermost ancestor, so a right-click inside a nested viewport resolved to it rather than to the diagram; the holder branch had already been corrected by `DEF-9` to count outermost-only, so the two branches contradicted each other on the same DOM; fix: `outermostSvg()` walks out to the top-level graphic and both branches use it; `src/index.ts`
  - 2026-08-22 reported: found by adversarial review before release; reproduced - a 400x260 chart with a 120x120 nested viewport exported 1920x1920 when the click landed inside the nested region
  - 2026-08-22 fixed (unreleased)
  - 2026-08-22 not covered by tests: rendered markdown strips inline `<svg>` and core renderers emit `<img>`, so no core-rendered fixture can carry a nested viewport
- [x] `DEF-15` **an image the exporter cannot read was offered and then failed silently** - MAJOR; `isImgSvg()` qualified on the URL alone, so a 404 or a cross-origin source passed the menu test and the export then died in `fetch` with only a console line; this repository's own README carries four shields.io badges that reproduce it; fix: an image must have loaded (`complete`, non-zero `naturalWidth`) to qualify, and every remaining failure raises a notification instead of a console line; `src/index.ts`
  - 2026-08-22 reported: found by adversarial review before release; reproduced both triggers - a missing `.svg` gave `getBBox is not a function`, a cross-origin badge gave `TypeError: Failed to fetch`, neither visible to the user
  - 2026-08-22 fixed (unreleased): regression for the 404 case covered by 'hides both items on a source that failed to load'; the cross-origin case cannot be resolved at menu time, so it is the notification that answers it
- [x] `DEF-16` **a raster image inside a `<foreignObject>` hid the items instead of exporting its chart** - LOW; the `DEF-6` early return fired before the ancestor search, so a right-click on a raster label inside an SVG refused rather than resolving the chart containing it; the failure direction was safe, but the user had clicked a region of an exportable graphic; fix: an image that is not itself SVG falls through to its ancestor `<svg>` only, never to the holder search, so `DEF-6` stays closed; `src/index.ts`
  - 2026-08-22 reported: found by adversarial review before release
  - 2026-08-22 fixed (unreleased)
- [x] `DEF-17` **a percentage-sized inline SVG exported at the wrong aspect ratio** - LOW; `width="100%" height="100%"` - the standard responsive-SVG idiom - had its unit stripped to `100`/`100`, so the export was square; a 400x260 chart came out 1920x1920, stretched 1.54x, with no error; fix: `width`/`height` are trusted only when unitless or `px`, otherwise resolution falls through to the `viewBox` branch that already handles it; `src/index.ts`
  - 2026-08-22 reported: found by adversarial review before release
  - 2026-08-22 fixed (unreleased)
  - 2026-08-22 not covered by tests: only the inline-SVG path reaches it, and the `<img>` path is saved by `naturalWidth`
- [x] `DEF-18` **uppercase `.SVG` was recognised in the image viewer but not in rendered markdown** - LOW; the blob branch tested `/\.svg$/i` while the URL branch used a case-sensitive `endsWith('.svg')`, so the same file was exportable when opened and not when referenced; pre-existing, not introduced by the DEF-6..DEF-12 work; fix: both branches match case-insensitively; `src/index.ts`
  - 2026-08-22 reported: found by adversarial review before release
  - 2026-08-22 fixed (unreleased): regression covered by 'recognises an uppercase .SVG extension'

- [x] `DEF-19` **the image viewer offered an export that could never run** - CRITICAL; every export from the image viewer failed with `TypeError: Failed to fetch` and no file, on every SVG file, from the moment it opened; cause: JupyterLab 4.6 changed `ImageViewer._render()` to revoke the viewer's blob URL inside the image's own `load` handler, so the URL leaves the blob registry before the graphic is on screen and `imgToPng`'s `fetch(img.src)` cannot read it back; the `DEF-15` guard cannot see this - `complete` and `naturalWidth` describe the decoded bitmap, which outlives the URL, so the image looks healthy and the item is offered; fix: read the markup from the document model (`context.model.toString()` on the owning `.jp-MainAreaWidget`), which is what the viewer itself renders from and outlives the URL, and offer the item only when that model resolves; `src/index.ts`
  - 2026-09-02 reported: reported from a live workbench as a console pair - `blob:.../<uuid> net::ERR_FILE_NOT_FOUND` followed by `[SVG Extension] Could not copy this graphic as PNG TypeError: Failed to fetch`
  - 2026-09-02 root cause: instrumented `URL.createObjectURL` / `revokeObjectURL` in the live document under galata; the viewer's URL is created at `ImageViewer._render` and revoked from an `HTMLImageElement` load listener, while a control blob minted in the same document fetches fine. Confirmed in the shipped bundle: `_render` registers `n=()=>{...URL.revokeObjectURL(t)}` on the image's `load` and `error` events. `@jupyterlab/imageviewer` 4.5.7 revoked only the previous URL, which is why the path used to work
  - 2026-09-02 fixed (unreleased): document-model source added; the three pre-existing image-viewer tests all asserted the menu was offered and none performed an export, which is how a path broken for every file stayed green. Regression covered by 'exports the file, whose blob URL is already revoked', which asserts the URL really is dead before exporting so it cannot quietly pass on a JupyterLab that keeps it alive; mutation restoring the URL-only read turns it red with no download at all
  - 2026-09-02 also fixed: the filename hash was taken from `img.src`, a uuid minted afresh on every re-render, so two exports either side of a re-render or a reopen named the same unchanged file differently; it now hashes the document text, pinned by the reopen half of the same test
  - 2026-09-02 accepted cost: `keyOf` and the filename hash now walk the document text rather than a short URL, and `keyOf` runs on every `isVisible`/`isEnabled` probe - about 200 ms of main-thread work per Save on a 20 MB file. Not remedied: hashing the key would trade the bytes for a collision that exports the wrong graphic, which is the DEF-6 class. The retention half was remedied - both commands now drop `lastResolvedKey` when they finish, so a large file is not held until the next right-click

## Command lifecycle

- [x] `DEF-4` **stale right-click target exported from a closed document** - MEDIUM; the recorded contextmenu target was never cleared, so a palette or programmatic invocation resolved a graphic from a document already closed and named the file after an unrelated focused tab; it also pinned the detached DOM subtree for the session; fix: `isConnected` guard that nulls the field, plus removal of the two palette registrations that were the only user-reachable path to it; `src/index.ts`
  - 2026-08-21 reported: found by adversarial review before release; reproduced end-to-end - closed the notebook, invoked Save as PNG from the palette, got an 86837-byte 1920x1248 PNG of the closed document's graphic
  - 2026-08-21 fixed: fixed (unreleased): isConnected guard plus palette registrations removed
  - 2026-08-21 not pinned by a test, and cannot be: with the palette registrations gone there is no user-reachable way to invoke a command without a fresh right-click, so the scenario is only constructible through `commands.execute`
- [x] `DEF-5` **non-Element contextmenu target threw out of isVisible** - LOW; a synthetic `contextmenu` dispatched on `document` (another extension, or automation) set the recorded target to a non-Element, and the unchecked cast made `closest` throw inside `isVisible`; Lumino calls it without try/catch, so menu construction aborted for every extension after the native menu had already been suppressed; fix: `instanceof Element` check; `src/index.ts`
  - 2026-08-21 reported: found by adversarial review before release; reproduced - TypeError: e.closest is not a function, four times during one menu render
  - 2026-08-21 fixed: fixed (unreleased): instanceof Element check added
  - 2026-08-21 not pinned by a test, and cannot be: the recorded target is only non-Element at menu-open if the synthetic event is itself what opens the menu, and JupyterLab core throws on that same event first, so the menu is lost either way. The guard stops this extension contributing to that failure; it cannot be observed from outside
- [x] `DEF-10` **`findSvgTarget()` mutated shared state, so one transient detach voided the whole gesture** - MAJOR; the `isConnected` guard also nulled `lastContextMenuTarget`, and the function runs four times per menu open, so a single frame in which any one probe saw the node detached destroyed the record permanently even after the identical node was re-attached; JupyterLab's windowed notebook removes and re-inserts cell nodes during scroll, so this was reachable without the document changing; fix: the predicate returns null without clearing the field - the next right-click overwrites it; `src/index.ts`
  - 2026-08-21 reported: found by adversarial review before release; A/B on the same DOM churn - probing while detached left `isVisible` false and the export dead after re-attach, not probing left it working
  - 2026-08-21 fixed (unreleased): guard made pure
  - 2026-08-22 not pinned by a test, and cannot be: observing it needs a node detached and re-attached between the four `isVisible` probes of a single menu open, which the harness cannot schedule
- [x] `DEF-11` **`isVisible` and `execute` disagree within one gesture, and the failure is silent** - MAJOR; Lumino evaluates `isVisible` when the menu opens and never again, while `execute` re-resolves at click time, so any re-render between the two - theme switch, markdown re-render, live-updating output - leaves an offered item that does nothing; the graphic stays on screen, the click produces no download and no message, only a `console.error`; reachable via the exact node replacement `RenderedMermaid.renderModel` performs
  - 2026-08-21 reported: found by adversarial review before release; reproduced - right-clicked a mermaid diagram, replaced the wrapper's innerHTML as core does, item still offered, `Save as PNG` produced nothing
  - 2026-08-21 open: the DEF-4 `isConnected` guard is what makes this reachable; before it the export succeeded from the detached node. Both candidate remedies add mechanism - a user-visible failure notice, or recording the click coordinates and re-deriving the element with `elementFromPoint` - so neither is taken without a decision on which
  - 2026-08-22 fixed (unreleased): the coordinate remedy, taken because it makes the action work rather than only reporting that it did not. The `contextmenu` listener now records the point and the owning `.jp-MainAreaWidget` id alongside the element; resolution falls back to `document.elementFromPoint` only when the recorded node has left the DOM, and only when the element found there belongs to the same widget. A re-render keeps that id, a closed document does not, so the fallback cannot export a graphic the user never right-clicked - which is what kept DEF-4 from being reopened by it. Resolution itself was extracted to `resolveFrom(element)` so both paths run identical rules; regression covered by 'still exports after the graphic re-renders under the open menu'
